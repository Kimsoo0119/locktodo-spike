## 렌즈 1 — 가정 검증

### D1-1. "잠금화면 위 글래스 패널"은 거짓 전제다 (치명)
mockup A/C 의 핵심 셀링포인트는 "잠금화면 위에 떠 있는 반투명 글래스 카드"(mockups.html:71 "잠금화면 위에 떠 있는 패널 느낌")다. 그런데 실제 구현 `LockActivity`는 OS 잠금화면 위에 뜨는 **별도 풀스크린 Activity**이고([LockActivity.kt L18-21](cursor://file/Users/ga/Desktop/code/personal/locktodo-spike/app/src/main/java/com/example/locktodo/LockActivity.kt:18)), A 테마 배경은 `linear-gradient(#2b1f54 → #0d0a1f)` **불투명 그라데이션**이다(design-tokens.md:15). 즉 사용자의 월페이퍼/OS 잠금화면을 완전히 덮어버린다. 글래스 카드가 blur 로 비출 "뒤 배경"은 OS 잠금화면이 아니라 **자기 자신의 그라데이션**뿐이다. blur 효과의 존재 이유(뒤가 비쳐 보임)가 성립하지 않는다. 컨셉의 근거가 무너진다.

### D1-2. 시계는 OS 잠금화면 시계와 100% 중복된다
스펙 3-1 은 "상단 큰 시계(시:분)+날짜, 1분 갱신"을 핵심으로 둔다(SPEC L23). 그러나 화면을 켜면 Android OS 잠금화면이 **이미 시계와 날짜를 그린다**. LockActivity 가 그 위를 불투명 배경으로 덮고 또 시계를 그리는 것이므로, 사용자 입장에선 "내 폰 기본 잠금화면 시계를 가리고, 똑같은 시계를 다시 보여주는" 동작이다. 추가 가치가 없고, 갱신 타이밍이 OS 보다 늦으면 OS 시계와 **다른 시각**을 보여주는 신뢰 붕괴가 발생한다. "왜 OS 시계를 가리고 자체 시계를 그려야 하는가"에 스펙이 답하지 못한다.

### D1-3. 3테마 사용자 선택은 스파이크 단계 오버엔지니어링 (YAGNI)
스파이크/검증 단계 앱이다(기능만 검증 완료). 그런데 첫 디자인부터 테마 3종 + 선택 UI + SharedPreferences 영속 + 메인/잠금 양쪽 반영(SPEC L44-47)을 요구한다. "사용자가 테마를 고른다"는 가정 자체가 검증된 적 없는 수요다. 잘 만든 기본 테마 1개로 4대 UI 문제(SPEC L10-14)는 전부 해결된다. 테마 3개는 4대 문제 해결과 **독립적인 별도 기능**인데 같은 작업에 묶여 핵심(가독성/위계 개선) 검증을 지연시킨다.

### D1-4. 테마는 "토큰만 바꿔 렌더"로 끝나지 않는다
SPEC L47 "한 컴포넌트가 토큰만 바꿔 렌더"라고 단정하지만, 테마 간 차이는 색 토큰이 아니라 **구조**다: 체크박스 모양(A/C 라운드사각 vs B 원형, SPEC L38), 배경(그라데이션 vs 단색), blur 유무(A/C 있음 vs B 없음), 카드 그림자 유무(B만 shadow). 이건 색 변수 교체가 아니라 분기 로직이다. "토큰화로 유지보수 비용 안 든다"는 주장은 근거가 없다.

## 렌즈 2 — 리스크 / 실패 모드

### D2-1. blur 는 API 31 미만에서 동작하지 않는다 (치명)
A/C 테마가 `backdrop-filter: blur`(mockups.html:20,48)에 의존한다. Android 네이티브에서 실시간 blur(`RenderEffect.createBlurEffect`)는 **API 31(Android 12)+ 전용**이다. 그런데 이 앱은 `setShowWhenLocked` 기준 **API 27(Android 8.1)부터** 동작한다([LockActivity.kt L18](cursor://file/Users/ga/Desktop/code/personal/locktodo-spike/app/src/main/java/com/example/locktodo/LockActivity.kt:18)). API 27~30 단말에서는 blur 가 무시되어 카드가 그냥 `rgba(255,255,255,.10)`(A) / `.7`(C) 반투명 단색으로 렌더된다. A 의 경우 다크 배경 위 10% 흰색 = 거의 안 보이는 카드, 즉 **레이아웃 붕괴**다. 스펙에 최소 SDK / blur fallback 정의가 없다.

### D2-2. 완료 텍스트 muted 대비가 WCAG AA 미달 (가독 실패)
- B 완료 텍스트 `#b6bac3` on 흰 카드 `#ffffff`(design-tokens.md:27): 대비비 ≈ **1.7:1**. AA 본문 기준 4.5:1, 큰 글씨 3:1 양쪽 다 미달.
- C 완료 텍스트 `#c9a392` on 흰 카드 `rgba(255,255,255,.7)`(design-tokens.md:38): 대비비 ≈ **2:1** 수준, 역시 미달.
- A 완료 텍스트 `#8a85a8`(design-tokens.md:18) 도 반투명 카드 위에서 경계.

"완료는 일부러 죽인다"는 의도는 이해되나, 취소선이라는 보조 단서가 있어도 **텍스트 내용 자체를 읽을 수 없을 정도**로 죽이는 게 맞는지 기준이 없다. "완료 항목도 내용은 식별 가능해야 하는가"에 스펙이 답해야 한다. 수치 목표가 전혀 없다.

### D2-3. 미완 체크박스 외곽선이 사라진다
A 미완 체크박스 외곽선 `rgba(255,255,255,.5)`(design-tokens.md:19)는 다크 배경에선 보이지만 **반투명 흰 카드(흰 10%) 위**에선 흰 50% 외곽선 → 거의 안 보임. "체크 안 한 항목이 체크박스 없이 텍스트만 떠 있는" 상태가 된다. 핵심 인터랙션(체크) 어포던스 상실.

### D2-4. 라이트 테마(B)를 잠금화면에 띄우면 야간 눈부심
B 배경 `#f4f5f7`(거의 흰색)을 잠금화면에 풀스크린으로 띄운다. 밤에 화면 켜면 OS 다크 잠금화면 대신 **흰 화면 플래시**가 터진다. 비목표에서 "다크모드 자동전환 안 함"(SPEC L18)이라 명시했으므로, 시스템 다크모드 사용자가 B 를 고르면 이 눈부심을 막을 장치가 없다.

### D2-5. 테마 3종 × (메인+잠금) × (빈/일반/대량) QA 매트릭스 폭증
테마 3 × 화면 2 × 상태(빈/소량/대량/긴텍스트) 4 × blur지원/미지원 2 = **48조합**. 스파이크에서 감당 불가. 회귀 QA 부담이 디자인 가치보다 클 수 있다.

## 렌즈 3 — 누락 / 엣지케이스

### D3-1. 잠금화면 대량 항목(100개) 처리 미정
LockActivity 는 `ScrollView`다([LockActivity.kt L29](cursor://file/Users/ga/Desktop/code/personal/locktodo-spike/app/src/main/java/com/example/locktodo/LockActivity.kt:29)). 잠금화면(잠금 안 풀린 상태)에서 사용자가 100개 카드를 스크롤한다는 시나리오가 자연스러운가? 카드 높이가 화면을 넘으면 시계가 밀려 올라가나, 카드만 스크롤되나? 스펙 3-1 에 카드 최대 높이 / 항목 수 상한 / "잠금화면엔 미완 N개만" 같은 규칙이 없다.

### D3-2. 긴 텍스트 / 줄바꿈 / ellipsize 미정
mockup 은 "장보기" 같은 짧은 텍스트뿐(mockups.html:67). 한 줄 넘는 할 일("내일 오전까지 팀 회의 자료 정리하고 공유 드라이브 업로드")이 들어오면 1줄 자르기(…)인지 2줄 wrap 인지 row 높이가 어떻게 되는지 정의 없음. 취소선이 멀티라인에서 어떻게 그려지는지도 미정.

### D3-3. 가로 모드 미정
시계 64sp(design-tokens.md:8) + 상단 padding 70px(mockups.html:17). 가로 모드에서 시계가 세로 공간 대부분을 먹어 카드가 안 보인다. orientation lock 인지, 가로 별도 레이아웃인지 스펙에 없음.

### D3-4. 폰트 스케일(접근성) 확대 시 붕괴
시계 `56~64sp`(design-tokens.md:8)는 sp 라 시스템 글꼴 확대(최대 200%)에 따라 128sp 까지 커진다 → 시계 한 줄이 화면 폭 초과. 반대로 dp 고정하면 저시력 접근성 무시. 두 길 다 정의 안 됨.

### D3-5. 시계 갱신 시 깜빡임 — 현재 구조와 충돌
현재 `refresh()`는 `removeAllViews()` 후 전체 재생성이다([LockActivity.kt L38-39](cursor://file/Users/ga/Desktop/code/personal/locktodo-spike/app/src/main/java/com/example/locktodo/LockActivity.kt:38)). 여기에 시계를 같은 컨테이너에 넣고 "1분마다 갱신"을 같은 방식으로 하면 1분마다 화면 전체가 재빌드되어 깜빡인다. 시계 갱신을 어떤 메커니즘(`ACTION_TIME_TICK` 리시버 vs Handler postDelayed)으로 하고, 갱신 시 **시계 TextView 만 부분 갱신**할 것인지 스펙에 전혀 없다. 분 경계(예: 9:41:58 에 화면 켜면 2초 뒤 9:42) 동기화도 미정.

### D3-6. 잠금화면 콘텐츠 노출(프라이버시) 미정
`setShowWhenLocked(true)`로 할 일 텍스트가 **잠금 안 푼 상태에서 그대로 노출**된다([LockActivity.kt L19](cursor://file/Users/ga/Desktop/code/personal/locktodo-spike/app/src/main/java/com/example/locktodo/LockActivity.kt:19)). "병원 예약", "이별 통보" 같은 민감 항목이 폰 주운 사람에게 보인다. 민감 항목 숨김/마스킹 옵션이 디자인 범위인지 명시 없음.

### D3-7. 메인 빈 상태 미정
잠금화면 빈 상태 문구는 있다(SPEC L28). 그러나 메인(MainActivity) 첫 실행 시(할 일 0개) 화면이 어떻게 보이는지 정의 없음. 현재는 입력창+버튼만 덩그러니([MainActivity.kt L77-95](cursor://file/Users/ga/Desktop/code/personal/locktodo-spike/app/src/main/java/com/example/locktodo/MainActivity.kt:77)).

### D3-8. 삭제 인터랙션이 아직 "열린 질문"인데 컴포넌트 규칙은 확정됨
SPEC L34 는 "✕ 아이콘 또는 스와이프"로 본문에 적어놓고, L61 에서 같은 걸 "열린 질문"으로 미결 처리한다. 스와이프 삭제면 실수 삭제 방지(undo/확인)가 필요한데 그 정의가 없다. 현재 코드는 확인 없는 즉시 삭제([MainActivity.kt L91](cursor://file/Users/ga/Desktop/code/personal/locktodo-spike/app/src/main/java/com/example/locktodo/MainActivity.kt:91))라 데이터 유실 리스크.

## 렌즈 4 — 측정 / 검증 가능성

### D4-1. 완료 기준이 순환 정의·주관적이다
SPEC 7 "완료 기준"이 "devil review 4-pass 전원 통과"(L57)를 포함한다. 즉 이 리뷰가 통과를 정의하는데 스펙은 그 리뷰 통과를 완료 기준으로 삼는 **순환 참조**다. "4대 문제 해결"(L55)도 검사 방법(누가/무엇으로 판정)이 없다.

### D4-2. 대비 수치 목표가 없다
"가독성 최고"(mockups.html:85) 같은 주관 서술뿐. AA 4.5:1 / AAA 7:1 / 큰글씨 3:1 중 어느 기준을 목표로 하는지, 완료/미완/날짜/시계 각 텍스트의 목표 대비비가 없다. 검증 불가. (실측하면 D2-2 처럼 떨어진다.)

### D4-3. blur 성능 / fps 기준 없음
"저사양에서 깨짐"을 검증하려면 목표 단말(최소 사양)·목표 fps(예: 잠금 진입 60fps, jank < 16ms)가 있어야 한다. 없음. "blur 켜고 잠금 진입이 버벅인다"를 무엇으로 합격/불합격 판정하나.

### D4-4. 측정 가능한 항목이 단 하나
정량으로 검사 가능한 건 "터치 영역 ≥ 48dp"(SPEC L40, design-tokens.md:7) 뿐이다. 나머지(여백, 위계, 감성)는 전부 정성. "디자인 개선됨"을 객관 입증할 지표 집합이 사실상 없다.

### D4-5. 구현 방식 미결인데 실구현이 완료 기준
SPEC 6 은 Compose vs XML 을 "리뷰에서 결정"(L51)으로 미루면서, SPEC 7 완료 기준은 "3테마+시계+4대문제 실구현"(L55)을 요구한다. blur·테마·시계 구현 난이도는 Compose/XML 에 따라 크게 다른데, 그 결정을 미룬 채로 실구현 일정을 완료 기준에 넣는 건 검증 불가능한 계획이다.

## 이번 라운드 스펙이 반드시 답해야 할 결함 TOP 5

1. **글래스/blur 컨셉의 근거 붕괴 (D1-1 + D2-1)** — LockActivity 가 OS 잠금화면을 불투명하게 덮으므로 blur 가 비출 배경이 없고, 게다가 네이티브 blur 는 API 31+ 전용이라 27~30 단말에선 A 카드가 사실상 안 보인다. "blur 를 쓰는 이유"와 "API 31 미만 fallback"을 스펙이 답해야 한다.

2. **자체 시계의 존재 이유 (D1-2)** — OS 잠금화면 시계와 100% 중복이며 갱신 지연 시 OS 와 다른 시각을 표시한다. "왜 OS 시계를 가리고 자체 시계를 그리나", "갱신 메커니즘과 OS 동기화"를 답해야 한다.

3. **완료/미완 텍스트·체크박스 대비 미달 (D2-2 + D2-3)** — B/C 완료 텍스트 대비비 약 1.7~2:1(AA 미달), A 미완 체크박스 외곽선이 카드 위에서 소실. 목표 대비비 수치와 "완료 항목 내용 식별 보장 여부"를 정의해야 한다.

4. **시계 갱신 깜빡임 + 실구현 메커니즘 (D3-5 + D4-5)** — 현재 전체 재빌드(`removeAllViews`) 구조에 1분 갱신을 얹으면 화면 전체가 깜빡인다. 부분 갱신 방식과 구현 스택(Compose/XML) 결정을 완료 기준 이전에 확정해야 한다.

5. **검증 불가능한 완료 기준 (D4-1 + D4-2 + D4-4)** — "devil 4-pass 통과"는 순환 참조, 대비/성능 수치 목표 부재, 측정 가능 항목이 터치영역 하나뿐. "디자인 개선됨"을 객관 판정할 정량 지표 집합을 스펙이 제시해야 한다.

### 부차 (TOP5 외, 그러나 답 필요)
- 3테마 선택 = 스파이크 단계 YAGNI (D1-3), "토큰만 바꿔 렌더" 비용 과소평가 (D1-4)
- 라이트 테마 야간 눈부심 (D2-4), QA 매트릭스 48조합 (D2-5)
- 대량/긴텍스트/가로/폰트확대/프라이버시/메인 빈상태/삭제 undo (D3-1~3-8)

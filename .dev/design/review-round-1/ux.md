# LockTodo 디자인 리뷰 라운드 1 — UX / 사용성

> 리뷰어 페르소나: 시니어 UX 리서처 / 사용성 전문가
> 대상: SPEC-design.md, design-tokens.md, mockups.html, MainActivity.kt, LockActivity.kt (현재 프로그래매틱 구현)
> 작성: 2026-06-07

핵심 사용 맥락: **잠금화면에서 한 손, 1~2초, 화면 안 보고도 누를 수 있어야 한다.** 데스크톱 GTD 앱이 아니라 "스쳐 지나가며 체크"하는 글랜서블 위젯이다. 아래 지적은 모두 이 맥락 기준이다.

---

## A. 잠금화면 인터랙션 (가장 중요)

### 1. 체크 토글에 즉각적 피드백이 없다 — 누른 게 됐는지 모른다
현재 `LockActivity.refresh()`는 토글 후 다음 `onResume` 때나 전체 목록을 다시 그린다. 탭 직후 시각 변화·촉각 피드백이 전혀 없다.
**왜 문제:** 잠금화면은 사용자가 화면을 자세히 안 본다. "눌렀는데 됐나?"가 확인 안 되면 한 번 더 누르게 되고(완료→미완 되돌림), 결국 잠금 해제해서 확인한다. 글랜서블 앱의 존재 이유가 무너진다.
**개선:**
- 탭 즉시 체크박스 채움 애니메이션(150~200ms) + `view.performHapticFeedback(HapticFeedbackConstants.CONFIRM)` 진동.
- 텍스트 취소선·muted 전환도 즉시. 전체 `removeAllViews()` 재렌더 대신 해당 row만 갱신(깜빡임 제거).
- 소리는 기본 끔(잠금화면은 공공장소 가능성). 진동만.

### 2. 탭 타깃이 체크박스 아이콘에만 걸려 있어 너무 작다
목업의 box는 24~26dp. 잠금화면에서 24dp 아이콘만 정확히 맞히는 건 한 손 엄지로는 빗나가기 쉽다.
**왜 문제:** Android 권장 최소 터치 영역은 48dp. 시각 박스는 24dp여도 **탭 히트영역은 row 전체(체크박스+텍스트, 높이 ≥56dp)** 여야 한다. 잠금화면은 조준 정밀도가 평소보다 낮다(걸으면서, 한 손).
**개선:** row 전체를 클릭 리스너로 묶고 최소 높이 56dp. 시각 박스는 24dp 유지하되 padding으로 히트영역 확보.

### 3. 오터치 방지 장치가 전혀 없다 — 주머니/들 때 의도치 않은 체크
서비스가 `ACTION_SCREEN_ON`마다 LockActivity를 띄운다. 알림 확인하려 화면만 켰을 때도 할 일 카드가 뜨고, 그 위를 스치면 체크된다.
**왜 문제:** 완료 취소·복구 수단이 없는 상태(아래 4번)에서 오터치는 곧 데이터 손상이다. 잠금화면 위젯의 최대 불만 요인.
**개선(택1 이상):**
- 체크는 **단순 탭이 아니라 탭 후 짧은 확인 영역** 대신, 오터치 빈도가 낮은 인터랙션 검토. 최소한 row 사이 간격을 넉넉히(현재 11~14dp padding은 좁음 → row 간 8dp 이상 gap).
- "방금 체크" 항목에 3초간 실행취소 스낵바/되돌리기 노출(4번과 통합).

### 4. 실수로 체크/삭제했을 때 복구(Undo) 경로가 없다 — 치명적
`TodoStore.toggle/remove`는 즉시 영구 저장(SharedPreferences). 잠금화면엔 삭제가 없지만 체크는 있고, 메인엔 삭제가 있다. 둘 다 되돌리기 불가.
**왜 문제:** 잠금화면은 오터치 확률이 본질적으로 높다(3번). 되돌릴 수 없는 파괴적 동작을 확인 없이 즉시 커밋하는 건 사용성 원칙 위반(에러 복구 가능성).
**개선:**
- 체크/삭제 직후 **Undo 스낵바 3~5초** (메인). 잠금화면은 스낵바가 안 어울리니 토글이 멱등(다시 탭하면 원복)인 점을 시각적으로 명확히.
- 삭제는 soft-delete(휴지통/최근삭제) 또는 최소한 메인에서 Undo 필수.

### 5. 카드 "글래스 blur"가 가독성 도박이다 — 잠금화면 배경 위라면
스펙/토큰은 A·C에 `backdrop-filter: blur`를 쓴다. 하지만 LockActivity는 **앱이 풀스크린 배경(테마 그라데이션)을 직접 그린다.** 실제 OS 잠금화면 배경(사용자 사진 등) 위가 아니다. 그렇다면 blur는 사실상 의미 없고, 만약 향후 진짜 wallpaper 위 오버레이로 바꾸면 흰 글씨가 밝은 배경사진에서 안 보일 수 있다.
**왜 문제:** "잠금화면 위에 떠 있는 느낌"이라는 컨셉과 "앱이 배경을 다 칠한다"는 구현이 어긋나 있다. 텍스트 대비가 배경에 따라 들쭉날쭉해질 위험.
**개선:** 결정 필요 — (a) 앱이 불투명 배경을 그린다(현재, 대비 안정적, blur 무의미하니 토큰에서 blur 빼고 반투명 카드는 단색 위 알파로) vs (b) 실제 wallpaper 투과. spec §3-1에 명시할 것.

## B. 접근성 (WCAG) — 측정값 기반

실제 토큰 색으로 대비를 계산했다(글래스 카드는 배경과 알파 블렌딩한 유효 배경색 기준). **AA: 본문 4.5:1, 큰 글씨/UI 컴포넌트 3:1.**

### 6. 완료(muted) 텍스트 대비가 세 테마 모두 AA 미달
| 테마 | 완료 텍스트 / 유효배경 | 대비 | 판정 |
|------|----------------------|------|------|
| A | #8a85a8 / 카드(#312c4c) | **3.76:1** | 본문 AA 미달 |
| B | #b6bac3 / #fff | **1.94:1** | 심각 미달 |
| C | #c9a392 / 카드(#fff4ed) | **2.12:1** | 심각 미달 |
**왜 문제:** "완료를 죽인다"는 디자인 의도는 맞지만, 완료 항목도 **읽을 수는 있어야** 한다(무엇을 끝냈는지 확인·되돌림 판단). 특히 B/C는 거의 안 보이는 수준. 저시력·야외 햇빛에서 사라진다.
**개선:** 완료 텍스트 대비를 최소 3:1(취소선이 있으니 본문 4.5 완화 여지 있으나 3:1은 사수). 권장값: B muted를 #8a8f9c급(약 3.5:1), C muted를 #a07a64급(약 3.5:1)으로 어둡게. "죽임"은 색보다 **취소선+불투명도**로 표현하고 색 대비는 확보.

### 7. 날짜 텍스트 대비 미달 (B·C)
| 테마 | 날짜 / 배경 | 대비 |
|------|------------|------|
| B | #9aa0ad / #f4f5f7 | **2.4:1** |
| C | #b07d63 / #ffd9c2 | **2.68:1** |
(A는 8.66:1 양호.)
**왜 문제:** 날짜는 14sp 작은 글씨라 큰 글씨 예외(3:1)도 못 받고 본문 4.5 기준 적용. 시계 옆 보조정보지만 잠금화면에서 자주 보는 핵심 정보다.
**개선:** B 날짜 #6b7280급, C 날짜 #8f5d44급으로 어둡게.

### 8. 체크박스 외곽선(미완) 대비가 낮아 "빈 체크박스"가 안 보인다 (B·C)
| 테마 | 미완 외곽선 / 배경 | 대비 |
|------|-------------------|------|
| B | #d4d7de / #fff | **1.44:1** |
| C | #e8a87c / 카드 | **1.88:1** |
**왜 문제:** UI 컴포넌트 경계는 3:1 필요. 미완 체크박스가 안 보이면 "여기 탭하면 체크된다"는 어포던스가 사라진다. 특히 빈 상태에서 할 일이 "그냥 텍스트"처럼 보임.
**개선:** 미완 외곽선을 3:1 이상으로(B #aab0bb, C #d2895c급). 2px → 2.5px도 도움.

### 9. C 테마 완료 체크의 흰 ✓ 대비 미달
코랄 accent #ff8a5c 위 흰색 ✓ = **2.32:1** (A 보라 #7c6cff 위 흰색은 양호, B 인디고는 4.51 양호).
**왜 문제:** 완료 표시의 핵심 시그널인 체크마크가 가장 따뜻한 테마에서 흐릿. 완료/미완 구분이 약해진다(스펙이 지적한 기존 문제 2의 재발).
**개선:** C accent를 약간 어둡게(#f5743f급, 흰 ✓ 대비 3:1+) 하거나 ✓를 진한 갈색(#5b3a2e)으로.

### 10. 텍스트 크기 / 동적 글꼴 대응
잠금화면 할 일 텍스트 16sp(목업)·20sp(현재 코드). 시스템 글꼴 확대(Accessibility) 시 레이아웃 검증 안 됨.
**왜 문제:** 잠금화면은 글랜서블이라 오히려 글자가 더 커야 유리한데, 16sp는 야외/노안에 작다. 그리고 sp 단위라 사용자 글꼴 확대 시 카드가 깨질 수 있음.
**개선:** 본문 17~18sp 기본. 긴 텍스트·큰 글꼴에서 줄바꿈/말줄임 동작 정의(11번).

## C. 상태 설계

### 11. 긴 텍스트 처리 규칙이 없다 — 줄바꿈 vs 말줄임 미정의
목업은 짧은 한 줄("아침 운동")만 보여준다. "팀 회의 자료 준비하고 김부장님께 공유드리기" 같은 실제 입력 시 동작 미정의.
**왜 문제:** 잠금화면 카드 높이는 제한적. 무한 줄바꿈이면 카드가 화면을 넘기고, 말줄임이면 내용 손실. 입력 검증(길이 제한)도 없다(`TodoStore.add`).
**개선:** 잠금화면은 **2줄까지 표시 후 말줄임**(…), 메인은 전체 표시. 입력 길이 소프트 제한(예 60자) + 카운터. row는 텍스트 길이와 무관히 최소높이 고정.

### 12. 빈 상태가 텍스트 한 줄뿐이라 약하다
현재 "할 일이 없습니다"(코드) / 스펙 "오늘 할 일이 없어요". 일러스트·CTA 없음.
**왜 문제:** 빈 상태는 첫인상이자 온보딩 순간. 잠금화면에서 빈 상태면 "이 앱 뭐하지?"가 된다. 다만 잠금화면에선 추가가 불가하므로 CTA가 애매.
**개선:**
- 잠금화면 빈 상태: 긍정 메시지("오늘 할 일 다 끝냈어요 🎉" vs "아직 등록된 할 일이 없어요")를 **완료로 비운 경우 / 원래 없는 경우** 구분.
- 메인 빈 상태: "+ 첫 할 일을 추가해보세요" 입력창으로 시선 유도.

### 13. 할 일이 많을 때 잠금화면 스크롤 동작이 위험
현재 ScrollView. 잠금화면에서 스크롤 제스처가 OS 잠금화면 dismiss/노티 셰이드와 충돌할 수 있고, 스크롤 중 오터치 체크 위험(3번과 결합).
**왜 문제:** 글랜서블 위젯에 긴 스크롤 리스트는 부적합. 10개 넘으면 "보고 지나가는" 용도를 벗어난다.
**개선:** 잠금화면은 **미완 항목 우선 정렬 + 상위 N개(예 5~6개)만 표시**, "외 N개"는 잠금 해제 후 메인에서. 완료 항목은 잠금화면에선 하단으로 보내거나 접기.

### 14. 완료 항목의 정렬·잔존 정책 미정의
체크해도 목록 그 자리에 남는다(취소선). 다음 날 리셋되는지, 완료가 쌓이는지 불명확(`Todo`에 날짜 필드 없음, spec 비목표에 날짜 제외).
**왜 문제:** 매일 쓰는 잠금 할 일인데 완료가 계속 쌓이면 카드가 완료 항목으로 가득 차 미완이 묻힌다. 글랜서블 가치 하락.
**개선:** 완료를 목록 하단으로 내리는 정렬은 비목표 위반 아님(데이터 변경 없음). 최소한 "완료 항목 잠금화면에서 접기" 토글. 일일 리셋은 스코프 밖이면 spec §8에 보류 명시.

## D. 플로우

### 15. 추가 → 잠금화면 반영 경로가 사용자에게 안 보인다
메인에서 추가 후 잠금화면 갱신은 `onResume` 재로드에 의존. 추가한 게 잠금화면에 뜬다는 확신을 주는 피드백이 없다.
**왜 문제:** 첫 사용자는 "메인에 추가한 게 잠금화면에 진짜 나오나?"가 핵심 의문. 이게 확인 안 되면 앱 가치 자체를 의심.
**개선:** 추가 직후 가벼운 확인("잠금화면에 추가됐어요") 또는 메인에서 잠금화면 미리보기를 상시 노출.

### 16. 권한/서비스 온보딩이 버튼 3개로 노출 — 순서·상태·실패가 안 보인다
현재 MainActivity는 "권한 허용" "서비스 시작" "미리보기" 버튼 3개가 평면 나열(스펙도 문제 3으로 지적). 더 큰 문제는 **각 단계의 완료 여부와 순서**가 안 드러난다는 것.
**왜 문제:** 오버레이 권한 → 알림 권한(33+) → 서비스 시작은 **순서 의존**이고 각각 실패할 수 있다(사용자가 설정에서 거부). 현 UI는 "지금 어디까지 됐고 뭘 더 해야 잠금화면이 뜨는지"를 못 알려준다. 권한 거부 시 빈 화면만 남는 dead-end.
**개선:**
- 상태형 온보딩 체크리스트: ①오버레이 권한 ②알림 권한 ③서비스 켜기 — 각 항목에 현재 상태(완료/필요) 표시, 미완만 액션 노출.
- 모든 단계 완료 시 배너를 "정상 작동 중"으로 축소(spec §3-2 방향과 일치).
- 권한 영구 거부 감지 시 설정 딥링크 안내.

### 17. 테마 변경 즉시성 — 잠금화면이 떠 있는 동안의 반영
스펙 §5는 "메인·잠금화면 모두 반영", SharedPreferences 저장. 하지만 잠금화면이 백스택에 떠 있는 상태에서 테마를 바꾸면 즉시 반영될지(다음 `onResume` 재생성 의존) 불명확.
**왜 문제:** 테마 선택은 즉시 미리보기가 핵심 만족 요소. "고르는 순간 바뀐다"가 안 되면 어느 게 적용됐는지 혼란.
**개선:** 메인의 테마 칩 선택 시 메인 화면 자체가 즉시 그 테마로 프리뷰(현재 칩만 강조하지 말 것). 잠금화면은 다음 표시 때 반영으로 충분(명시).

### 18. "미리보기" 버튼이 실제 서비스 흐름과 분리돼 혼란
"잠금화면 미리보기"가 권한·서비스와 같은 위계의 버튼. 사용자는 미리보기와 실제 동작을 구분 못 한다.
**왜 문제:** 미리보기는 디버그/확인용인데 메인 1급 액션으로 올라와 있어 "이걸 눌러야 켜지나?" 오해.
**개선:** 미리보기는 온보딩 완료 후 보조 위치로(또는 설정). 메인 주인공은 할 일 목록.

## E. 삭제 인터랙션 — ✕ vs 스와이프 (spec §8 답변)

### 19. 권장: **메인은 ✕ 아이콘 + Undo, 스와이프는 보조(또는 1차 출시 제외)**
| 방식 | 장점 | 단점(이 앱 맥락) |
|------|------|------------------|
| ✕ 아이콘(우측) | 발견성 높음, 오작동 적음, 구현 단순 | row가 약간 복잡 |
| 스와이프 삭제 | 깔끔, 모던 | **발견성 낮음(숨은 제스처)**, 스크롤과 충돌, 오스와이프 삭제 위험, 접근성(스위치/토크백) 어려움 |
**왜 이 결론:** (1) 이 앱은 항목 수가 적고 삭제 빈도 낮다 → 숨은 제스처의 효율 이득이 작다. (2) 스와이프는 잠금화면 스크롤·OS 제스처와 충돌(13번). (3) 발견성·접근성에서 명시적 ✕가 우위. (4) 어느 쪽이든 **Undo가 없으면 둘 다 위험**(4번) — 삭제 방식보다 복구 가능성이 본질.
**결론:** 1차는 **✕ 아이콘(터치영역 48dp) + 삭제 즉시 Undo 스낵바**. 스와이프는 원하면 "보조 제스처"로 추가하되 단독 의존 금지. **잠금화면엔 삭제 자체를 두지 말 것**(오터치·복구불가 조합이 최악) — 현재 스펙대로 체크만 유지가 옳다.

## F. spec §8 열린 질문에 대한 UX 의견 (요약)

- **구현 Compose vs XML:** UX 관점에선 **Compose 권장**. 위 1번(즉시 토글 애니메이션·부분 갱신), 6~9번(테마별 토큰 스왑), 12번(빈 상태)이 선언형에서 훨씬 싸게 구현된다. 단 잠금화면 위 렌더 안정성은 둘 다 검증 필요.
- **삭제:** ✕ + Undo (19번). 잠금화면 삭제 없음.
- **테마 선택 위치:** 1차 **메인 상단 세그먼트**(3개뿐이라 설정 화면 과함) + 선택 즉시 메인 프리뷰. 항목이 늘면 설정으로 이전.
- **시계 포맷:** **OS 12/24h 설정을 따른다**(별도 토글 만들지 말 것 — 사용자는 시스템 시계와 다르면 혼란). 날짜는 "6월 7일 토요일" 식 한글 풀표기 유지, 단 대비(7번) 수정.

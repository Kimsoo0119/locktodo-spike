# 디자인 리뷰 라운드 1 — 비주얼 디자이너(UI) 관점

> 대상: `SPEC-design.md`, `design-tokens.md`, `mockups.html`, 현재 구현(`MainActivity.kt`/`LockActivity.kt`)
> 페르소나: 시니어 비주얼 디자이너 · 작성 2026-06-07
> 결론 한 줄: 방향(3테마 + 시계 + 목록 주인공화)은 옳습니다. 다만 **토큰이 "색표"에 머물러 있고 시스템이 아닙니다.** 상태색·간격 스케일·타이포 weight·구현 한계(blur) 토큰이 비어 있어 지금 그대로 구현하면 테마마다 손맛으로 값이 갈립니다.

## A. 시각 위계 (무엇이 주인공인가)

**1. 잠금화면의 주인공 서열은 맞으나, 카드 섹션 라벨이 테마마다 다릅니다.**
목업에서 테마 A만 "오늘 할 일"(`.ct`, uppercase) 라벨이 있고 B/C에는 없습니다(`mockups.html:64` vs `:78`,`:92`). 같은 앱의 같은 화면이 테마에 따라 정보 구조가 달라지면 위계가 아니라 변덕으로 읽힙니다.
→ **왜**: 테마는 "스킨(색·질감)"이지 "정보 구조"가 아니어야 합니다. 라벨 유무는 모든 테마에서 동일해야 일관성이 섭니다. 권장: 시계가 이미 주인공이므로 카드 라벨은 **전 테마 공통으로 유지하되 muted 톤의 작은 캡션**으로 통일(스캔성 +, 위계 침범 −). 라벨을 둘 거면 `.ct` 토큰을 B/C에도 정의해야 합니다.

**2. 완료 항목이 목록 최상단에 위치(`mockups.html:65`)해 위계가 거꾸로입니다.**
"아침 운동(완료)"이 맨 위, 미완료가 아래입니다. 취소선+회색으로 죽인 항목이 시선의 첫 진입점을 차지합니다.
→ **왜**: 시선은 위→아래로 흐르고, 죽인 요소가 상단에 있으면 "할 일이 끝났나?"라는 잘못된 첫인상을 줍니다. 잠금화면은 0.5초 글랜스가 핵심이라 더 치명적입니다. 권장: **미완료 먼저, 완료는 하단으로 sink**(또는 완료는 목록에서 숨기고 "n개 완료" 접기). 정렬 규칙을 스펙에 명시.

**3. 메인 화면의 버튼 과다 → 배너 축소 방향은 시각적으로 옳습니다.**
현재 `MainActivity.kt:32-43`의 큰 버튼 3개가 화면 상단을 점유해 목록(주인공)을 밀어냅니다. SPEC §3-2의 배너 1줄 축소가 정답입니다.
→ **왜**: 권한/서비스 시작은 **1회성 설정 행위**입니다. 영구 버튼으로 두면 매번 시각 비용을 지불합니다. 권장: 권한 미충족 시에만 뜨는 **상단 인라인 배너(아이콘+한 줄+작은 액션)**, 충족되면 collapse. 진행성 노출(progressive disclosure)로 목록이 항상 주인공이 됩니다. "미리보기" 버튼은 개발용이므로 릴리즈 빌드에서 숨기거나 오버플로 메뉴로.

## B. 타이포그래피 스케일

**4. 타입 스케일이 3개(time 56–64 / date 14 / item 16)뿐이고 중간 단계가 비어 있습니다.**
카드 라벨, 입력 필드, 추가 버튼, 빈 상태, 메인 타이틀의 사이즈가 토큰에 없습니다.
→ **왜**: 스케일이 듬성하면 구현 시 임의값(18,20,22…)이 끼어들어 리듬이 깨집니다. 권장: **모듈러 스케일**로 5~6단계 정의 — 예: Display 60 / Title 22 / Body 16 / Label 13 / Caption 12. 한 번 정하면 모든 화면이 같은 자를 씁니다.

**5. 폰트 weight가 토큰화되어 있지 않은데, 테마마다 weight가 크게 다릅니다.**
시계 weight가 A 300(thin) / B 600 / C 700(`mockups.html:18,46,46`), 항목 텍스트도 A 400 / B 500 / C 600으로 제각각입니다.
→ **왜**: weight는 색만큼 강한 "톤" 신호입니다. 의도된 차이(A=우아, C=친근)라면 **명시적 토큰**(`weight.clock`, `weight.item`)으로 박아야 재현 가능합니다. 지금은 암묵값이라 구현자가 default로 통일해버리면 테마 개성이 사라집니다.

**6. 시계 숫자에 tabular figures(고정폭 숫자) 지정이 없습니다.**
시계는 1분마다 갱신됩니다(SPEC §3-1). 비례폭 숫자면 "11:11"→"12:00" 전환 시 글자폭이 출렁입니다.
→ **왜**: 틱마다 레이아웃이 미세하게 흔들리는 건 시계 컴포넌트의 전형적 결함입니다. 권장: `fontFeatureSettings("tnum")` 또는 고정폭 숫자 폰트. 작지만 완성도를 가르는 디테일.

## C. 여백 / 그리드

**7. 간격 스케일(spacing scale)이 없어 모든 여백이 ad-hoc 값입니다.**
카드 마진 A 18 / B·C 16, 시계 top A 70 / B 74 / C 72, 카드 내부 패딩 A 18·18·8 / B 8·6 / C 14·10(`mockups.html:20,34,48`). 규칙이 없고 눈대중 값입니다. 게다가 HTML px라 dp 변환 기준도 모호합니다.
→ **왜**: 8dp(또는 4dp) 베이스 그리드가 없으면 컴포넌트마다 1~2px씩 어긋나고, 그게 모이면 "정렬이 안 된 느낌"이 됩니다. 권장: **`space.xs/sm/md/lg/xl = 4/8/12/16/24dp`** 토큰 정의 후 모든 마진·패딩을 거기서만 꺼내 쓰기. 시계 top 70/74/72 같은 미세차는 통일.

**8. 항목 row 높이가 48dp 터치 타깃을 아슬하게 밑돌 수 있습니다.**
테마 A는 세로패딩 11px×2 + 박스 24 = 46px로 48dp 미만(`mockups.html:22-23`). SPEC §4는 ≥48dp를 요구하는데 토큰 값이 이를 못 지킵니다.
→ **왜**: 잠금화면에서 잠금 해제 없이 정확히 탭해야 하는 컴포넌트라 터치 타깃이 더 중요합니다. 권장: row **최소 높이 48dp 보장**을 토큰 제약으로 못 박고, 시각 패딩과 별개로 터치 영역을 확장(invisible padding).

## D. 색 대비 / 일관성

**9. 코랄 accent(C #ff8a5c) 위의 흰 ✓ 대비가 약합니다.**
흰색 체크 on #ff8a5c는 약 2:1 수준으로, WCAG 비텍스트 3:1에 못 미칩니다(A 보라·B 인디고는 여유 있음).
→ **왜**: 체크 표시는 "완료"라는 핵심 상태의 유일한 시각 신호입니다. 밝은 accent에서 흰 체크가 뭉개지면 완료/미완료 구분력이 떨어집니다. 권장: 테마 C는 체크 색을 **흰색 대신 진한 갈색(#5b3a2e)** 으로 쓰거나, 체크 두께/그림자 보강. accent별 "on-accent" 색을 토큰화.

**10. 테마 B 완료 텍스트(#b6bac3 on #fff)는 대비가 낮습니다(약 1.9:1).**
취소선이 이미 완료를 알리므로 의도된 de-emphasis이지만 가독성 한계선입니다.
→ **왜**: 완료 항목도 "무슨 일이었는지" 읽혀야 다시 체크 해제 판단이 됩니다. 취소선+회색은 좋되 너무 죽이면 정보가 사라집니다. 권장: muted를 한 단계 진하게(예 #9aa0ad)거나, 완료는 **opacity 0.5**로 처리해 명도 대비를 일정하게 유지.

**11. accent 사용 규칙(어디에 쓰고 어디엔 안 쓰는지)이 없습니다.**
accent는 테마당 1색이라고만 정의되어 있고, 체크 채움 외에 추가 버튼·선택된 테마 칩·입력 포커스 등에 쓸지 규칙이 없습니다.
→ **왜**: accent는 "지금 가장 중요한 것"을 가리키는 희소 자원입니다. 무절제하게 쓰면 위계가 무너집니다. 권장: **accent = 완료 체크 + 1차 액션(추가)에만**. 선택된 테마 칩은 accent 테두리, 포커스는 accent 1px — 등 사용처를 토큰 주석으로 명문화.

## E. 부족한 토큰 (가장 큰 갭)

**12. 상태(state) 토큰이 통째로 비어 있습니다.** 아래는 구현 들어가기 전 반드시 채워야 할 목록입니다.

| 누락 토큰 | 왜 필요한가 | 권장 |
|---|---|---|
| `pressed`/ripple | Android는 모든 탭에 눌림 피드백이 표준. 없으면 "죽은 화면"처럼 느껴짐 | 테마별 pressed 오버레이(예 다크=white .08, 라이트=black .06) |
| `accent-pressed` | 체크/버튼 누를 때 accent가 어두워져야 물리감 | accent를 8~12% darken |
| `disabled` | 빈 입력일 때 추가 버튼 비활성 등 | 텍스트 .38 / 배경 .12 (Material 관례) |
| `focus` (입력) | 메인 입력 필드 포커스 표시 | accent 1.5px underline/border |
| `destructive`(삭제) | 삭제 ✕ 색. 빨강 계열인지 muted인지 미정 | 평상시 muted, 확인 단계서 빨강 |
| `divider` (A·C) | B만 정의(#f0f1f4). A/C는 "여백 구분" 방식이지만 미문서화 | A/C는 "no divider, spacing model"임을 명시 |
| 빈 상태(empty) | SPEC은 문구만, 색·크기·아이콘 미정 | muted 색 + Body 사이즈 + 선택적 일러스트/아이콘 |
| `on-accent`(체크색) | 9번 참조. 흰 체크 고정 가정이 C에서 깨짐 | 테마별 명시 |
| elevation (A·C) | B는 shadow 정의, A/C는 blur+border만 | 13번 참조(폴백 필요) |

**13. 글래스(blur) 토큰에 구현 폴백이 없습니다 — 가장 위험한 갭.**
테마 A/C는 `backdrop-filter: blur`에 의존(`mockups.html:20,48`)합니다. Android의 실시간 블러(`RenderEffect`)는 **API 31(Android 12)+에서만** 동작하고 그 이하에선 무시됩니다.
→ **왜**: 폴백이 없으면 구형 기기에서 카드가 그냥 반투명 흰 박스가 되어 "글래스" 컨셉이 통째로 무너집니다. 잠금화면은 기기 스펙을 가리지 않습니다. 권장: **blur 토큰 + "blur 불가 시 solid semi-opaque 대체값"을 쌍으로** 정의(예 A: blur20 / fallback rgba(40,32,80,.92)). 이건 디자인-구현 합의가 필요한 의사결정이라 라운드에서 결정.

## F. 컴포넌트 디테일

**14. 체크박스 ✓를 텍스트 글리프(`content:"✓"`)로 그리고 있습니다.**
목업이 폰트 체크 문자를 씁니다(`mockups.html:25,39,53`). 폰트마다 ✓의 두께·중심이 달라 픽셀 정렬이 흔들립니다.
→ **왜**: 체크는 이 앱에서 가장 자주 보는 마이크로 인터랙션입니다. 벡터(아이콘/Path)로 그려야 어느 폰트/기기에서나 동일하게 또렷합니다. 권장: ✓를 **vector drawable**로, 선 두께·라운드 캡 토큰화.

**15. 체크 토글에 상태 전환 모션 스펙이 없습니다.**
미완→완료 시 채움/체크가 즉시 점프합니다.
→ **왜**: "잠금 해제 없이 체크하는 손맛"이 이 앱의 핵심 경험입니다. 무모션이면 만족감이 없습니다. 권장: **150–200ms 채움 scale + 체크 draw-in**, 텍스트 취소선 fade. 모션 duration/easing을 토큰화(과하지 않게).

**16. 시계 컴포넌트 스펙이 사이즈뿐입니다.**
12/24h, AM/PM 표기, 앞자리 0(9:41 vs 09:41), 콜론 깜빡임 여부, 날짜 포맷이 미정.
→ **왜**: 시계가 잠금화면의 주인공인데 디테일이 비어 있으면 주인공이 흐릿해집니다. 권장: 17번 참조(포맷은 시스템 따르기). 콜론은 **고정(깜빡임 없음)** 이 최신 트렌드라 무난.

**17. 카드 radius가 22~26으로 테마마다 다른데, 이건 의도로 보이나 정렬이 필요합니다.**
A/C 24~26, B 22(`design-tokens.md` 공통). 작은 차이라 의도(B=날카로운 미니멀, C=둥근 친근)는 이해되나 입력 필드·버튼·칩의 radius 토큰이 없어 카드만 둥글고 나머지는 제각각이 될 위험.
→ **왜**: radius는 테마 "성격"을 만드는 핵심 형태 토큰입니다. 카드만 정하고 다른 컴포넌트를 비우면 형태 언어가 깨집니다. 권장: `radius.card / radius.field / radius.chip / radius.checkbox`를 테마별 한 세트로.

## G. §8 열린 질문 — 디자인 의견

**18. 테마 선택 위치: 메인 상단 인라인(세그먼트/칩) 권장.**
→ **왜**: 테마가 3개로 적고, 개인화는 이 앱의 1급 매력 포인트입니다. 설정 화면에 숨기면 발견성이 떨어지고, 무엇보다 **선택 즉시 아래 목록이 그 테마로 바뀌는 라이브 프리뷰**를 줄 수 없습니다. 메인 타이틀 바로 아래 세그먼트 컨트롤 + 하단 목록 실시간 반영이 최적. 단, 향후 테마가 5개를 넘으면 설정으로 이전. (배너/타이틀과 시각 경합하지 않도록 세그먼트는 muted, 선택만 accent.)

**19. 시계 포맷: 디자인이 고르지 말고 시스템 설정을 따르기 권장.**
→ **왜**: 12/24h는 사용자 OS 설정에 이미 있는 선호입니다. 디자이너가 하드코딩하면 누군가에겐 항상 틀립니다. `DateFormat.is24HourFormat()`을 따르되, **타이포 측면 규칙만** 디자인이 소유: 24h는 `09:41`(앞자리 0), 12h는 `9:41 AM`(AM/PM은 시각 1/3 크기 muted). 날짜는 `6월 7일 토요일`(목업) 유지하되 로케일 대응. 이건 "디자인 결정"이 아니라 "시스템 존중 + 타이포 규칙"으로 정리.

**20. 구현 방식(Compose vs XML): 비주얼 관점에선 Compose 권장(부차 의견).**
→ **왜**: 3테마를 토큰 교체로 렌더(SPEC §5)하는 구조는 Compose의 `Theme`/`CompositionLocal`에 정확히 들어맞고, 체크 모션(15번)·blur(`Modifier.blur`/`RenderEffect`)도 Compose에서 다루기 쉽습니다. 단 엔지니어 결정 사항이라 비주얼 측 선호로만 기록.

## 핵심 개선점 5 (우선순위)

1. **상태 토큰 통째 추가** (pressed/disabled/focus/destructive/on-accent/empty) — 지금 토큰은 색표지 시스템이 아님. 구현 전 필수(§E-12).
2. **글래스(blur) 폴백 토큰 정의** — A/C가 Android 12 미만에서 컨셉 붕괴. blur 불가 시 solid 대체값 쌍으로(§E-13).
3. **간격 스케일 + 타입 스케일/weight 토큰화** — 4/8dp 그리드와 모듈러 타입 스케일, 테마별 weight 명시(§B-4·5, §C-7).

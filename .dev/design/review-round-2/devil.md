## 0. 한 줄 결론

R1 결정은 **문서(decisions.md)에만** 반영됐고, **산출물(design-tokens.md / mockups.html / *.kt)은 R1 이전 그대로**다. "결정했다 ≠ 스펙에 반영됐다". 구현자가 진짜로 읽는 source of truth(토큰·목업·코드)는 R1 결함을 그대로 들고 있다. 게다가 R1이 R2로 미룬 두 항목(잠금화면 덮기 / 3테마 분기 비용)은 **코드를 보면 미룰 게 아니라 아키텍처를 무를 수준의 결함**이다.

## 1. R1 결함 → R2 닫힘 여부 판정

### R1-TOP1. 글래스/blur 컨셉 붕괴 (D1-1 + D2-1) → ❌ 절반만, 핵심 미해결

- D2 결정(blur 폐기 → 반투명 fill + 1px border)은 **API31 fallback 문제만** 덮었다. 그러나:
  - **산출물 미반영**: `design-tokens.md:15` 는 아직 `rgba(255,255,255,.10) + blur`, `:36` 도 `rgba(255,255,255,.7) + blur`. `mockups.html:20,48` 도 `backdrop-filter:blur` 그대로. **D2를 따른 흔적이 토큰/목업에 0**. 구현자가 토큰을 source of truth로 읽으면 blur가 그대로 살아난다. 결정과 산출물이 충돌하면 산출물이 이긴다.
  - **blur를 떼면 D2-3(체크박스 소실)·A카드 가독이 더 나빠진다**: A 카드는 blur 없는 `흰 10%` 단색이 되어 다크 배경 위에서 거의 안 보인다. D2는 "fill로 대체"만 말하고 **보이는 fill 값으로 토큰을 다시 정하지 않았다**. 문제를 blur→투명 fill로 옮겼을 뿐.
  - **컨셉 붕괴 본질(D1-1)은 그대로**: "잠금화면 위에 떠 있는 패널"(mockups.html:71)인데 우리가 OS 잠금화면을 불투명 그라데이션으로 통째 덮는다(아래 §2). 뒤에 비칠 게 없다는 모순은 손도 안 댔다.

### R1-TOP2. 자체 시계 존재 이유 (D1-2) → ❌ 명시적 미루기

- decisions.md:24 가 "덮는 방식이 옳은가는 R2에서 정리"로 **대놓고 연기**. 닫힌 게 아니다. D7은 시계 *구현*(ACTION_TIME_TICK·tabular)만 정했는데, 이건 "자체 시계를 그린다"를 이미 전제로 깔고 들어간 결정이다. 전제가 틀리면 D7 전체가 무효. §2에서 코드 근거로 이 전제를 깬다.

### R1-TOP3. 완료/미완 대비 미달 (D2-2 + D2-3) → ❌ 말로만 닫음

- D3가 "muted 색은 대비 충족값으로 **토큰 수정**"이라 적었지만 **`design-tokens.md`는 한 글자도 안 바뀜**:
  - B 완료 `#b6bac3` on `#ffffff` ≈ **1.7:1** (그대로)
  - C 완료 `#c9a392` on `rgba(255,255,255,.7)` ≈ **2:1** (그대로)
  - A 완료 `#8a85a8` (그대로)
- D3는 "취소선 + 불투명도"라 했지만 **목표 알파값도, 그 결과 대비비도 안 적음**. §9 검증 지표는 "토큰 쌍마다 계산 통과"라는데 **통과할 토큰 자체가 아직 존재하지 않는다**(미수정). 측정 대상이 없는 측정 기준.
- **D2-3(미완 체크박스 외곽선 소실)은 decisions 어디에도 언급 없음.** A 미완 외곽선 `흰 50%`가 blur 뗀 흰 10% 카드 위에서 소실 → 체크 어포던스 상실. 완전 누락.

### R1-TOP4. 시계 깜빡임 + 구현 스택 (D3-5 + D4-5) → ✅ 결정 레벨에선 닫힘

### R1-TOP5. 검증 불가능한 완료 기준 (D4-1 + D4-2 + D4-4) → ❌ 순환 참조 살아있음

## 2. 추궁 ① — OS 잠금화면을 불투명하게 덮는 설계 자체가 옳은가 (치명, 신규 근거)

R1은 이걸 "R2에서 정리"로 미뤘다. 코드를 보면 **미룰 사안이 아니라 아키텍처를 무를 결함**이다.

근거(코드):
- `ScreenService.kt:19-22` — `ACTION_SCREEN_ON` 을 받으면 **무조건** `LockActivity` 를 `FLAG_ACTIVITY_NEW_TASK` 로 띄운다. **`KeyguardManager.isKeyguardLocked` 체크가 없다.**
- `LockActivity.kt:18-21` — `setShowWhenLocked(true)` + `setTurnScreenOn(true)`, 자체 그라데이션 풀스크린(불투명).

여기서 나오는 치명 결함:

### ②-a. 잠긴 게 아니어도 튀어나온다
ACTION_SCREEN_ON 은 잠금 여부와 무관하게 화면 켜질 때마다 발생한다. 이미 폰을 푼 상태에서 화면을 잠깐 껐다 켜면(또는 홈/앱 사용 중 절전 후 복귀) **LockActivity가 홈/사용 중 앱 위로 튀어나온다**. "잠금화면 할 일"이 아니라 "아무 때나 끼어드는 전체화면 방해물". 스펙 §3-1 은 "잠금화면"만 말하고 잠금 상태 가드를 정의하지 않는다.

### ②-b. 네이티브 잠금 해제 동선을 우리가 막는다 — 사용자가 밀어올려도 우리 Activity는 안 사라진다
사용자 질문("밀어올리면 우리 Activity가 사라지지 않나?")의 답: **사라지지 않는다. 더 나쁘다.** 우리 LockActivity는 keyguard *위*에 뜬 별개 Activity다. swipe-to-unlock 어포던스는 keyguard(우리 뒤)에 있는데 우리 불투명 화면이 그걸 가리고 터치를 가로챈다. 우리 화면을 밀어올려도 keyguard 제스처가 아니므로 아무 일도 안 일어난다. 폰을 쓰려면 사용자가 back/home으로 우리 Activity를 **먼저 치워야** 비로소 OS 잠금화면이 드러나고, 거기서 다시 풀어야 한다. → **화면 켤 때마다 잠금 해제에 단계가 하나씩 추가된다.** 스펙에 "사용자가 LockActivity를 어떻게 해제/통과하는가" 인터랙션이 **전무**하다.

### ②-c. 그래서 ①의 답: 전체 대체는 틀렸다
"OS 잠금화면을 통째 대체"는 (a) 잠금 아닌 상황 오발동, (b) 네이티브 unlock 차단, (c) 뒤에 비칠 배경이 없어 글래스 컨셉 붕괴(§1)를 한꺼번에 만든다. 대안은 **잠금화면 위 패널이 아니라 ① keyguard 위에 콘텐츠만 얹되 unlock 제스처를 통과시키는 방식**이거나 **② 아예 별도 잠금화면 위젯/노티 컨트롤**인데, 셋 중 무엇인지 스펙이 R2에서 **반드시** 정해야 한다. 안 정하면 시계·테마·대비 논의 전부 사상누각.

## 3. 추궁 ② — "3테마는 토큰화로 완화"가 정말 되나 (decisions:25 미루기 검증)

부분 사실, 부분 거짓. 분리해서 본다.

- **토큰화 가능한 것**: 색(accent/text/muted/배경 brush)·radius·체크박스 corner는 `data class AppTheme` + `CompositionLocal` 로 값 주입 가능. 체크박스 "모양"도 A/C `RoundedCornerShape(8~9)` vs B `CircleShape` 를 *Shape 토큰*으로 넣을 수 있어 **구조 분기가 아니라 값 분기로 흡수 가능**하다. 여기까진 decisions 주장이 방어된다.
- **토큰으로 안 끝나는 것**:
  - 배경이 A/C는 `Brush.linearGradient`, B는 단색 → Brush 토큰으로 통일 가능(단색도 Brush). OK.
  - **그림자 B만 존재**(tokens:25). elevation 토큰 0/비0으로 흡수 가능. OK.
  - 그러나 **§1에서 깐 blur 모순**: A/C는 blur 전제, B는 없음. blur를 D2대로 진짜 폐기하면 세 테마 모두 fill+border로 통일되지만, 그러면 **A/C 차별화가 색뿐**이 되어 "글래스/따뜻한 카드" 정체성이 사라진다. 즉 토큰화로 비용은 줄지만 **테마 차별성 자체가 증발**. "분기 비용 완화"의 대가가 "테마 3개를 만들 이유 소멸"이다.
- **진짜 비용은 토큰이 아니라 QA**: R1 D2-5(48조합)는 decisions에서 답 없음. 토큰화해도 테마3 × 화면2 × 상태4 의 **시각 회귀 검증 표면적**은 안 줄어든다. "유지보수 완화"를 코드 분기로만 좁게 해석하고 검증 비용을 빼먹었다.

판정: "토큰만 바꿔 렌더"는 코드 측면 **대체로 참**이나, ① blur 폐기 시 테마 정체성 소멸, ② QA 비용 불변 — 이 둘을 스펙이 인정·정리해야 함. 현재 미정리.

## 4. 추궁 ③ — §9 정량 지표가 실제로 측정 가능한가

| 지표 | 측정 가능? | 결함 |
|------|-----------|------|
| 색 대비 토큰 쌍마다 ≥4.5/3:1 | 원리상 ✅ | **측정 대상이 없음**: 통과하는 수정 토큰이 아직 design-tokens.md에 없음(§1 TOP3). 현 토큰으로 돌리면 전부 fail. |
| 인터랙션 row ≥56dp | ✅ | 유일하게 진짜 측정 가능. 단 코드(CheckBox 위젯)는 미반영. |
| 시계 무깜빡임(부분 갱신) | ❌ | 판정 방법·임계값 없음. 프레임 드랍 기준? 육안? |
| 테마 전환 즉시 반영 | ❌ | "즉시"의 ms 임계값 없음. 잠금화면은 이미 떠 있는 Activity인데 메인에서 바꾼 prefs가 **언제 어떻게** 잠금화면에 전파되는지(재생성? observer?) 미정 → 측정 이전에 동작 정의가 없음. |
| 회귀 없음(에뮬 실측) | △ | 수동·1회성. 반복 가능 측정 아님. "실측"은 측정자 의존. |

결론: **객관·반복 측정 가능한 지표는 row 높이 하나**. 대비는 토큰 수정 후에야 측정 가능. 나머지 3개는 임계값 부재로 여전히 정성. R1-TOP5가 실질적으로 안 닫힌 이유.

## 5. 4렌즈 신규 치명 결함

### 렌즈 1 — 가정
- **N1-1 (치명)**: "ACTION_SCREEN_ON = 잠금 상황" 가정이 거짓. keyguard 가드 없음(§2-a). 잠금 아닐 때도 전체화면 침입.
- **N1-2 (치명)**: "사용자가 LockActivity를 자연히 통과해 폰을 쓴다" 가정이 거짓. unlock 동선 차단(§2-b). 해제 인터랙션 정의 0.
- **N1-3**: "테마는 메인에서 고르면 잠금화면에 즉시 반영"(D10/§9) 가정 — 잠금화면 Activity는 백그라운드에 떠 있을 수 있고, prefs 변경 전파 메커니즘 미정. 즉시 반영의 기술 경로 없음.

### 렌즈 2 — 리스크
- **N2-1**: 백그라운드 startActivity 제약(Android 10+). FGS 예외에 기댄 BAL(Background Activity Launch)은 OEM/버전별로 막힌다. 핵심 기능(화면 켜면 뜸)이 단말에 따라 **아예 안 뜰** 리스크. 스펙은 동작을 기정사실로 둠.
- **N2-2**: `setTurnScreenOn(true)` + 매 ACTION_SCREEN_ON 재기동 → 웨이크/재기동 루프·배터리. 상주 FGS. 범위 논의 없음.
- **N2-3**: 라이트 테마 B 야간 풀스크린 플래시(R1 D2-4) — decisions:28 미루기. 시스템 다크모드 사용자가 B 고르면 방어 없음.

### 렌즈 3 — 누락
- **N3-1 (치명)**: LockActivity 해제/통과 인터랙션 미정의(§2-b). 디자인 스펙인데 "이 화면을 어떻게 빠져나가는가"가 없다.
- **N3-2**: **산출물 동기화 누락** — decisions(D2/D3)와 design-tokens.md/mockups.html이 불일치. SPEC §5는 "토큰으로 분리해 구현"이라 토큰을 source of truth로 지정했는데 그 토큰이 결정을 안 따름. 구현자는 어느 쪽을 따르나? (R1 잔여 누락의 재발.)
- **N3-3**: R1 D3-1~3-8(대량/긴텍스트/가로/폰트확대/프라이버시/메인빈상태/삭제undo) 중 decisions에 들어온 건 삭제 undo(D4)뿐. 나머지 7개 미해결로 R2에 이월.

### 렌즈 4 — 검증 가능성
- **N4-1**: §9 측정 가능 지표 실질 1개(§4).
- **N4-2**: §7 완료 기준 순환 참조(devil 4-pass) 미제거(§1 TOP5).
- **N4-3**: "테마 즉시 반영" 등은 동작 정의 자체가 없어 테스트를 작성할 수조차 없음.

## R2에서 스펙이 반드시 답해야 할 잔여 결함 TOP 5

1. **OS 잠금화면 덮기 아키텍처 결정 (②-a/b/c, N1-1·N1-2·N3-1, 치명)** — keyguard 가드 없이 매 screen-on에 불투명 전체화면을 띄워 (a) 잠금 아닐 때도 침입하고 (b) 네이티브 unlock 동선을 막는다. "전체 대체 vs keyguard 위 패스스루 패널 vs 위젯/노티" 중 하나를 정하고, **사용자가 LockActivity를 어떻게 통과/해제하는지** 인터랙션을 정의해야 한다. 이게 안 정해지면 시계·테마·대비 전부 무의미.

2. **결정과 산출물의 불일치 해소 (N3-2, §1 TOP1·TOP3)** — D2(blur 폐기)·D3(muted 대비 충족 토큰)가 decisions.md에만 있고 design-tokens.md·mockups.html은 R1 그대로다. **토큰/목업을 실제로 D2·D3에 맞춰 다시 쓰고**, 그 수정 토큰으로 대비비를 재계산해 §9 "통과" 대상을 실재화해야 한다.

3. **대비·체크박스 어포던스 수치 확정 (R1-TOP3 잔여)** — B/C 완료 텍스트(1.7~2:1)와 A 미완 체크박스 외곽선(blur 제거 후 흰10% 카드 위 소실, decisions 누락)에 대해 목표 대비비·완료 알파값·"완료 항목 내용 식별 보장 여부"를 숫자로 정의.

4. **자체 시계의 존재 이유 + 테마 전파 메커니즘 (R1-TOP2, N1-3)** — 1번 아키텍처 결정에 종속. 덮기를 유지할 경우 "왜 OS 시계를 가리고 다시 그리나 + OS와 시각 동기화"를, 그리고 메인 테마 변경이 떠 있는 잠금화면에 **어떤 경로로 즉시 전파**되는지(observer/재생성)를 답해야 함. 정의 없이는 §9 "즉시 반영" 측정 불가.

5. **검증 기준의 순환 제거 + 측정 임계값 (R1-TOP5, N4-1·N4-2)** — §7에서 "devil 4-pass 통과" 순환 참조 삭제. §9의 "무깜빡임/즉시 반영/회귀"에 측정 방법과 수치 임계값(ms·프레임·체크리스트)을 부여해 측정 가능 지표를 1개→전부로.
